## Findings for this v0.1 scope

The delivery plan describes a 25-second diagnostic-only run with bounded `curl`, optional DNS lookup, finite ping, read-only local context, optional offline TShark, evidence references, and four diagnosis statuses. These upstream projects provide useful review patterns, but none establishes that exact runtime contract.

### Patterns to carry forward

1. **Write observations and falsifiers beside each diagnosis.** The Daymade skill requires a concrete artifact before treating a symptom as real, asks what observation would falsify a hypothesis, and limits conclusions to the compared path and workload. The isolation guide says A/B/A supports a causal contrast only if the original failure returns; if A succeeds after B, report causation as unestablished. Apply the lightweight form to v0.1: record supporting evidence, counterevidence, missing evidence, scope, and the next falsifying observation. This is documented methodology, not an automatic rule in an executable probe. ([skill](https://github.com/daymade/claude-code-skills/blob/cf0f48c818282003fb063a54cb51977e5aed259f/debugging-network-issues/SKILL.md), [isolation guide](https://github.com/daymade/claude-code-skills/blob/cf0f48c818282003fb063a54cb51977e5aed259f/debugging-network-issues/references/layered-isolation-experiment.md#return-to-original-a-b-a))

2. **Use counter-review to challenge conclusions, then filter findings.** Daymade defines counter-review as falsification work and filters findings for likelihood, cost, fit to the actual environment, and cheap verifiability. For a small diagnostic skill, keep the filter and independent review at the project review/evaluation layer; the cited skill's multi-agent process adds minutes of overhead and is not a per-run requirement. ([counter-review guide](https://github.com/daymade/claude-code-skills/blob/cf0f48c818282003fb063a54cb51977e5aed259f/debugging-network-issues/references/counter-review-pattern.md#the-four-question-filter))

3. **Check capabilities, then select explicit platform commands.** `network-mcp` implements a `capabilities` MCP tool for platform/runtime versions, selected binary availability, and active target/PCAP policy; its README recommends calling it first, but the server does not enforce order. `connectivity_agent.py` maps a fixed tool set to platform-specific argv arrays and per-process timeouts. Borrow local capability reporting and explicit OS command maps; keep the shared 25-second deadline, output caps, and target policy in our runner. ([capabilities README](https://github.com/labeveryday/network-mcp/blob/c18f717a2ac3156931201e78d02b6e0bbeb19d02/README.md#recommended-first-run), [capabilities implementation](https://github.com/labeveryday/network-mcp/blob/c18f717a2ac3156931201e78d02b6e0bbeb19d02/src/network_mcp/tools/capabilities.py), [platform command map](https://github.com/brocla/connectivity_agent/blob/692df554f8e28f55632a615ca7d77d350ee50b15/connectivity_agent.py#L61-L125))

4. **Preserve PCAP observation context, not just decoded fields.** Daymade's packet-capture guidance calls out interface selection, capture filters, timestamps/timezone, snap length, and collector exit/drop statistics; it warns that rotation count is neither a hard deadline nor a file-size bound. For this project's offline-only branch, keep the input hash, packet/frame references, filter/field recipe, capture window when known, truncation, and parse status with extracted facts. Do not turn those capture instructions into live capture defaults. ([packet-capture recipes](https://github.com/daymade/claude-code-skills/blob/cf0f48c818282003fb063a54cb51977e5aed259f/debugging-network-issues/references/packet-capture-recipes.md#file-limited-time-rotation), [capture comparison details](https://github.com/daymade/claude-code-skills/blob/cf0f48c818282003fb063a54cb51977e5aed259f/debugging-network-issues/references/packet-capture-recipes.md#match-packets-before-reporting-a-missing-fraction))

5. **Keep diagnostic scope separate from mutation.** Shuva's meta-skill labels T1–T6 read-only diagnostics and T9 remediation separately, and says the architect must not execute generated code. That separation supports a diagnostic-only release boundary. It does not make its generated endpoints safe by itself: the templates are stubs, not a hardened runtime. ([SOP skill](https://github.com/shuvajyotikar13/skills/blob/88dffefbf47f6bd7065c2daa48b1d6208420362f/netops-playbook-automation/SKILL.md), [T9 template](https://github.com/shuvajyotikar13/skills/blob/88dffefbf47f6bd7065c2daa48b1d6208420362f/netops-playbook-automation/templates/t9_closed_loop_remediation.py))

### Defaults not suitable for v0.1

- **Do not copy repair or approval recipes.** CacinieP's pinned skill says to start read-only and ask before changes, but its workflow has six stages (collect, classify, diagnose, analyze, resolve, verify), not a four-stage reversible-repair contract; examples include external probes, `curl -L`, and configuration changes. Shuva's T9 sample sets approval metadata but does not validate the returned token, and its later branch references `proposed_commands` assigned only in the no-token branch. Neither provides an enforced rollback transaction. ([CacinieP workflow](https://github.com/CacinieP/network-troubleshoot-skill/blob/e07d83a5293b4ace1b6a7ce8848e79469e73c7af/skills/network-troubleshoot/SKILL.md#safety-boundaries), [Shuva T9 template](https://github.com/shuvajyotikar13/skills/blob/88dffefbf47f6bd7065c2daa48b1d6208420362f/netops-playbook-automation/templates/t9_closed_loop_remediation.py))
- **Do not treat tool timeouts as a whole-run bound.** The connectivity agent's individual timeouts do not constrain cumulative calls, total output, or user/model repetition. v0.1 needs one runner-owned deadline and subprocess cleanup, not an open-ended autonomous tool loop. ([source](https://github.com/brocla/connectivity_agent/blob/692df554f8e28f55632a615ca7d77d350ee50b15/connectivity_agent.py#L80-L91), [agent loop](https://github.com/brocla/connectivity_agent/blob/692df554f8e28f55632a615ca7d77d350ee50b15/connectivity_agent.py#L280-L314))
- **Do not use the PII scanner as a privacy boundary.** The pinned script is a line-oriented regex scan with default `*.py` directory coverage. It reports matched values and line numbers; it stores a line snippet on each violation but the current report does not print that field. IP addresses are warnings, while the process exit code fails only on critical matches. It skips some comment/docstring/placeholder cases. It can be a review aid after hardening, but it does not redact runtime evidence or prove that reports contain no sensitive data. ([scanner patterns and allowlisting](https://github.com/shuvajyotikar13/skills/blob/88dffefbf47f6bd7065c2daa48b1d6208420362f/netops-playbook-automation/scripts/netops_pii_scanner.py#L90-L185), [report and exit status](https://github.com/shuvajyotikar13/skills/blob/88dffefbf47f6bd7065c2daa48b1d6208420362f/netops-playbook-automation/scripts/netops_pii_scanner.py#L243-L282))
- **Do not treat `network-mcp` policy as default-deny or a rate limiter.** It validates connectivity targets and blocks explicit metadata endpoints, but defaults to an empty allowlist and `block_private=false`. Hostnames are resolved for validation and used again by ping/traceroute/port checks; DNS lookup accepts a custom nameserver without validating that destination. RDAP starts at fixed `rdap.org` but follows redirects without visible final-target validation. Batch tools have default concurrency values (10 for ping/DNS, 20 for ports), but caller-adjustable concurrency and explicit list sizes; there is no per-client rate limit or CIDR-enumerating probe. These are static-source findings, not exploit tests. Test DNS rebinding, private-IP paths, custom resolver destinations, redirects and proxy behavior before treating these controls as SSRF defenses. ([target policy](https://github.com/labeveryday/network-mcp/blob/c18f717a2ac3156931201e78d02b6e0bbeb19d02/src/network_mcp/config.py#L61-L74), [target validation](https://github.com/labeveryday/network-mcp/blob/c18f717a2ac3156931201e78d02b6e0bbeb19d02/src/network_mcp/config.py#L278-L336), [DNS lookup](https://github.com/labeveryday/network-mcp/blob/c18f717a2ac3156931201e78d02b6e0bbeb19d02/src/network_mcp/tools/connectivity.py#L422-L468), [RDAP](https://github.com/labeveryday/network-mcp/blob/c18f717a2ac3156931201e78d02b6e0bbeb19d02/src/network_mcp/tools/external_intel.py#L20-L43), [batch tools](https://github.com/labeveryday/network-mcp/blob/c18f717a2ac3156931201e78d02b6e0bbeb19d02/src/network_mcp/tools/connectivity.py#L913-L1182))
- **Do not treat the reported PCAP maximum as a hard PCAP budget.** The implemented Scapy tools `pcap_summary`, `find_tcp_issues`, and `analyze_dns_traffic` return aggregate counts/timestamps/talkers and TCP/DNS summaries, not frame IDs or input hashes. `rdpcap` uses per-call `max_packets=100,000`; the reported config maximum is not clamped into those arguments, and no input-byte/deadline cap or truncation marker appears in the result models. `allowed_paths` are enforced after path resolution, but default paths include the working directory, temp directories, Documents, Downloads, and Desktop. ([PCAP readers](https://github.com/labeveryday/network-mcp/blob/c18f717a2ac3156931201e78d02b6e0bbeb19d02/src/network_mcp/tools/pcap.py#L84-L225), [TCP/DNS readers](https://github.com/labeveryday/network-mcp/blob/c18f717a2ac3156931201e78d02b6e0bbeb19d02/src/network_mcp/tools/pcap.py#L547-L887), [response models](https://github.com/labeveryday/network-mcp/blob/c18f717a2ac3156931201e78d02b6e0bbeb19d02/src/network_mcp/models/responses.py#L313-L396), [path resolution and allowlist](https://github.com/labeveryday/network-mcp/blob/c18f717a2ac3156931201e78d02b6e0bbeb19d02/src/network_mcp/config.py#L563-L599), [default paths](https://github.com/labeveryday/network-mcp/blob/c18f717a2ac3156931201e78d02b6e0bbeb19d02/src/network_mcp/config.py#L78-L97))
