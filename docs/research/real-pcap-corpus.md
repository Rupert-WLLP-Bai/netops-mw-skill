# Real capture corpus: offline v0.1 validation

**Historical pre-fix result: a reproducible DNS direction-count defect was found.** The [post-fix validation](real-pcap-postfix-validation.md) records the subsequent correction and new checks. Three published captures and six derived capture-impairment variants were analyzed with the existing v0.1 offline CLI. The nine actual runs below are distinct from the ten [designed lifecycle journeys](closed-loop-scenarios.json), which remain unexecuted. No device, service or ticket was changed and no live diagnostic probe was sent. This is not architecture approval, a release, or end-to-end incident recovery validation.

Source commit `c43d3f3d63d47a69f11cf2a73ca12d047fa6f577`; every run checked the source hashes recorded in its manifest against the local runtime. No runtime files were modified. Full aggregate results, commands, hashes and checks are in [real-pcap-corpus.json](real-pcap-corpus.json). Raw inputs, variants and run artifacts are retained only in ignored `.tools/pcap-corpus/`; they can contain sensitive traffic and must not be committed. `.gitignore` was verified.

## Reproducible DNS count defect

On web original, `tshark -2 -n -r INPUT -Y "dns.id && dns.flags.response == 0" -T fields -e frame.number` returns **111 query frames**, and the same filter with `== 1` returns **56 response frames**. The CLI reports **167 queries and 0 responses**, despite reporting response-code counts 44 code 0 and 12 code 3. Lab original independently yields **13 query and 13 response frames**; the CLI reports **26 and 0**. Both variants reproduce the mismatch (lab omission is 12/13 versus 25/0). The slow trace has no DNS fields, so its zero/zero match does not exercise this logic. `dns.id` includes DNS-dissector fields in LLMNR and mDNS; these are frame counts, not counts of DNS messages, requests or end-to-end transactions.

For a direct data-format example, web parent frame 30 is a response (`dns.flags.response == 1`); retained EK lists `dns_flags_response` as `["True"]`. `tshark -G fields` identifies this as `FT_BOOLEAN`. The existing summarizer tests only string `"1"`, number `1` or boolean `True`, so the string `"True"` falls into the query branch. This is evidence of a version/serialization handling defect; additional serialization and repeated-value tests are needed. Offline diagnosis currently derives its candidate from TCP retransmission indicators, and all nine actual diagnoses were `insufficient_evidence`; no changed diagnosis was observed or asserted. Response-code values remain in the aggregate, but those values do not repair the mislabeled direction counts.

A future fix should preserve these original failing artifacts, add a targeted regression using the traceable public capture, check Boolean string/numeric forms and missing/repeated values, rerun all nine files, and record full-suite and package results separately. Do not infer that a simulated omission is a network impairment or that synthetic short PCAPs establish operational accuracy.
