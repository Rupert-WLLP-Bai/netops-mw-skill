# Deep triage: tools and source-backed case patterns

**Checked:** 2026-11-12. This is research and a proposed extension, not a claim of implemented v0.2 functionality. The existing [delivery plan](../delivery-plan.md) defines v0.1, its 25-second deadline, and outstanding validation. No downloaded code was installed or run, no target was probed, and no external measurement was created for this research. Source pages below were read as published; moving documentation and default-branch URLs are **not commit pinned**, so adapter design must recheck the exact installed tool version and its output before implementation. Named release or incident dates are stated where available. No sample numbers below are measurements made by this project.

## Ranked recommendations

1. **Controlled single-target HTTPS comparisons.** The v0.1 replay diagnosis already matches normal and pinned requests under strict conditions, while live pinned collection is missing. Extend bounded live HTTP evidence with an explicitly selected normal-versus-address-pinned comparison and a separate IPv4-versus-IPv6 comparison. Preserve URL hostname, Host, SNI, certificate verification, method, port, proxy path and timestamps; report actual IP/family, negotiated protocol and individual failures. Keep repeated observations within an explicit shared budget. Only compare DNS-stage timings when the network path and connection semantics actually match. This is a proposed experiment, not evidence that a resolver caused a different CDN selection. [curl manual](https://curl.se/docs/manpage.html); [RFC 8305](https://www.rfc-editor.org/rfc/rfc8305).
2. **One bounded numeric path adapter.** Evaluate MTR first for finite report output and existing deployments, with Trippy as a candidate where structured flow-aware reports are demonstrably better. Preflight capabilities; specify destination, family, protocol, hop and probe limits, timeout, total deadline and output cap. Record per-hop sent/received, missingness, endpoint results and actual completion. An intermediate node's missing response is not proof of forwarding loss; ECMP and different protocols complicate comparison. Do not automatically escalate privileges. [MTR manual](https://github.com/traviscross/mtr/blob/master/man/mtr.8.in); [Trippy releases](https://github.com/fujiapple852/trippy/releases); [RFC 1812 §4.3.2.8](https://www.rfc-editor.org/rfc/rfc1812#section-4.3.2.8).
3. **Offline TCP expert evidence.** The v0.1 offline-PCAP branch already discovers fields and retains input and raw-event hashes, frame numbers, timestamps, streams and available expert flags, plus summary and coverage information. Add a structured per-stream timeline with finding-to-frame references, richer capture-origin, drop and visibility metadata, and optional opposite-end correlation. A suspected retransmission or unseen segment is a dissector inference about captured packets, not a proven failing link. [Wireshark TCP analysis](https://www.wireshark.org/docs/wsug_html_chunked/ChAdvTCPAnalysis.html); [display fields](https://www.wireshark.org/docs/dfref/t/tcp.html).

Later work: optional PMTU experiments; controlled throughput/load testing; external vantage measurements; then richer device telemetry. Each needs a separate explicit budget, sample tool output, platform/permission matrix and reproducible validation. Do not silently add these to v0.1 or assume any arbitrary public endpoint is a healthy control.

## Tool evidence and adapter fit

| Candidate | Evidence available and bounded use | Interpretation and adoption limits |
| --- | --- | --- |
| curl | The [manual](https://curl.se/docs/manpage.html) documents `--resolve`, `--ipv4`, `--ipv6`, timing and write-out fields; `--resolve` maps a hostname and port to supplied address while retaining the URL hostname. Compare ordinary and pinned requests, and family-specific requests, with verification enabled. | A proxy may resolve or connect differently; establish actual semantics or mark comparison ineligible. Connection reuse, negotiation, caches, path and server selection can change timings. Forced family failures do not by themselves identify why. The documentation is moving, not pinned. |
| MTR | The [owner manual](https://github.com/traviscross/mtr/blob/master/man/mtr.8.in) specifies report cycles, numeric output, per-hop loss/sent/latency and JSON; JSON depends on a build with Jansson. | Gate protocol, privilege and output support on installed build. Loss reflects responses to probes; compare downstream and destination response and business traffic before inferring forwarding loss. A finite deadline may yield partial results. |
| Trippy | [Owner releases](https://github.com/fujiapple852/trippy/releases) describe JSON reports and flow/Paris strategies; newer releases include trace start and end timestamps. A fixed flow tuple increases the chance of following one ECMP route, without guaranteeing it or the return path. | Output and privileges vary by release/platform; do not assume its unprivileged mode is available everywhere. Validate actual JSON schema and cap flow cardinality. |
| NextTrace | [NTrace-core](https://github.com/nxtrace/NTrace-core) documents traditional and MTR output modes, and its [MTR JSON contract](https://github.com/nxtrace/NTrace-core/blob/main/docs/mtr-json.md) distinguishes these formats. | The mutable documentation is not a tested installed version. IP/geographic annotations and possible external lookups introduce disclosure and attribution questions; select no enrichment until dependencies and privacy behavior are verified. Avoid parsing traditional JSON as MTR JSON. |
| tracepath | The [iputils manual](https://github.com/iputils/iputils/blob/master/doc/tracepath.xml) describes UDP path/PMTU discovery and numeric, family, packet-length and maximum-hop options. | Linux-specific. It sends traffic and uses a range of UDP ports; hop count is not a complete packet/time bound. Put it behind a runner deadline and explicit traffic budget; missing ICMP feedback can conceal a black hole. A detected PMTU is path/probe-specific, not an application guarantee. |
| Globalping / RIPE Atlas | [Globalping API specification](https://github.com/jsdelivr/globalping/blob/master/public/v1/spec.yaml) describes measurement creation, rate limits and reuse of the same probes via a prior measurement ID. [Globalping](https://github.com/jsdelivr/globalping) states measurement parameters and results are public. [RIPE Atlas measurement documentation](https://atlas.ripe.net/docs/getting-started/user-defined-measurements.html) describes user-defined measurements. | External measurement sends the target to a third party and its probes; public disclosure, rate/credit limits, availability and partial/asynchronous results must be explicit. Record selected actual probe/ASN/location/family, time, protocol, errors and measurement ID; remote vantage is not the user's local route or population sample. Reusing probes does not freeze route or time. |
| iperf3 / Flent | [iperf3 manual](https://software.es.net/iperf/invoking.html) describes client/server, duration, JSON, direction and stream controls; [Flent tests](https://flent.org/tests.html) describe RRUL and latency under load. | These generate substantial traffic and require a willing test server: later, explicit opt-in, with bandwidth, direction, duration, concurrency and recovery budgets. Results depend on both hosts, CPU, transport and test settings. iperf3 before 3.16 used one thread; the [FAQ](https://software.es.net/iperf/faq.html) says Windows is not officially supported. A speed result alone does not establish bufferbloat. |
| Linux `ss`, `ip`, `ethtool` | [iproute2 `ss` manual](https://git.kernel.org/pub/scm/network/iproute2/iproute2.git/tree/man/man8/ss.8) documents socket TCP details; [ip-route](https://git.kernel.org/pub/scm/network/iproute2/iproute2.git/tree/man/man8/ip-route.8.in) documents route lookup; [kernel statistics](https://docs.kernel.org/networking/statistics.html) distinguishes standard and driver-defined counters. | Later Linux-only contextual evidence should scope socket/interface, capture timestamps and use deltas only across matching identity and intervals. Counters vary by driver and may be unavailable; interfaces and unrelated flows share counters. Route lookup is a prediction, not proof of the actual path; do not use mutation commands. |
| Wireshark/TShark | [Wireshark TCP analysis](https://www.wireshark.org/docs/wsug_html_chunked/ChAdvTCPAnalysis.html) tracks connection state based on packets in the capture; its [TCP field reference](https://www.wireshark.org/docs/dfref/t/tcp.html) labels suspected retransmission and previous segments not captured. | Existing field discovery and hashed event artifacts retain frame IDs and scope; further structure must preserve these and check installed version/fields. Capture loss, midstream start, asymmetry, offload and filtering can affect interpretation; no live capture or keys are implied. |

## Public failure patterns and discriminating observations

The following are source-backed incidents or technical patterns, not claims that these experiments were performed on those historical incidents. The proposed comparisons are operator hypotheses, and a negative control is evidence that could weaken that hypothesis, not proof of its opposite.

1. **Resolver failure versus CDN steering.** Cloudflare's [October 2023 incident](https://blog.cloudflare.com/1-1-1-1-lookup-failures-on-october-4th-2023/) describes valid queries returning SERVFAIL after resolver DNSSEC validation failed. Separately, its [DNS cache description](https://blog.cloudflare.com/dns-cache-memory-optimization-1111/) notes ECS can yield client-network-dependent answers. Symptom: one resolver or destination appears slow or fails. Measure response code, resolver/transport, A/AAAA answers and timing, then matched hostname-preserving requests to an authorized common address. **Control:** same resolver and address with ordinary and pinned requests, repeated near in time. **Limit:** different addresses, POPs or caches confound DNS processing with steering; no local timing reveals resolver CPU.
2. **CNAME dependency versus client parsing.** Cloudflare's [2015 Dyn postmortem](https://blog.cloudflare.com/the-internet-is-a-cooperative-system-dns-outage-of-6-july-2015/) reports failures associated with CNAME-dependent origin resolution; its [January 2026 resolver report](https://blog.cloudflare.com/cname-a-record-order-dns-standards/) describes clients failing when answer record order changed. Measure full answer chain, status and resolver with a matched successful client or resolver. **Control:** same query and chain from an unaffected client. **Limit:** client-side resolution cannot prove a CDN's internal origin lookup or diagnose client parser code.
3. **IPv6 degradation hidden by fallback.** Cloudflare reports an [IPv6-only route leak on January 22, 2026](https://blog.cloudflare.com/route-leak-incident-january-22-2026/). [RFC 8305](https://www.rfc-editor.org/rfc/rfc8305) describes connection racing/fallback. Compare normal, forced IPv4 and forced IPv6 requests to the same hostname and method; record actual address, timing and errors. **Control:** repeated successful same-family request to an authorized comparison target. **Limit:** families can reach different servers and paths; a single family difference does not identify a route leak or prove the normal client used fallback.
4. **TLS name, certificate and ALPN.** [TLS SNI](https://www.rfc-editor.org/rfc/rfc6066#section-3) and [ALPN](https://www.rfc-editor.org/rfc/rfc7301) let a client present a server name and negotiate an application protocol. For a TLS error or protocol-specific failure, compare hostname-preserving requests to authorized selected IPs; record verification result, certificate identity where visible and negotiated protocol. **Control:** verified normal request and a second known-good authorized endpoint/configuration. **Limit:** do not disable verification to claim success; different IPs and protocol negotiation are multiple variables, and a certificate error alone does not identify its owner.
5. **Hop response loss versus forwarding loss.** Router [ICMP rate-limiting guidance](https://www.rfc-editor.org/rfc/rfc1812#section-4.3.2.8) allows ICMP errors to be limited. A trace with a silent middle hop and responding later hops should be compared with endpoint and application samples during the same window. **Control:** later-hop and destination responses plus business success. **Limit:** clean later replies weaken a blanket forwarding-loss claim but do not rule out intermittent, selective or protocol-specific loss; return paths and ECMP may differ.
6. **PMTU black hole and tunnels.** Cloudflare's [PMTU analysis](https://blog.cloudflare.com/path-mtu-discovery-in-practice) describes oversized packets being dropped when the relevant ICMP feedback cannot reach the sender. Small exchanges can succeed while larger transfers stall. Compare bounded size-sensitive observations and path/PMTU information, with tunnel and family recorded. **Control:** small exchange and an authorized alternative path. **Limit:** no ICMP response is inconclusive, probe UDP and application traffic may take different paths, and changing tunnel MTU is outside this diagnostic proposal.
7. **Load-sensitive latency versus raw throughput.** Cloudflare's [network-quality explanation](https://blog.cloudflare.com/aim-database-for-internet-quality/) distinguishes idle latency from latency under load; [Flent](https://flent.org/tests.html) supplies concurrent traffic/latency test patterns. Compare repeated idle/load/recovery windows and both transfer direction and latency. **Control:** same target in an idle recovery window. **Limit:** correlation does not identify the queue or establish bufferbloat; host saturation, server limits and other traffic are alternatives. Load generation requires explicit authorization and limits.
8. **Application/service failure versus network reachability.** Cloudflare's [July 2019 incident](https://blog.cloudflare.com/cloudflare-outage/) reports widespread HTTP 502 responses after a bad deploy caused CPU saturation. Record business HTTP status, TLS/connection completion, target and same-window control; a completed TCP handshake can coexist with application failure. **Control:** a matched healthy endpoint/service where available. **Limit:** 502 and successful network setup cannot identify the actual faulty component or reproduce that incident's internal cause.
9. **DNS failure as a symptom of route failure.** Meta's [October 2021 engineering account](https://engineering.fb.com/2021/10/05/networking-traffic/outage-details/) explains that a backbone configuration change disconnected its data centers and disrupted services including DNS. Compare resolver responses with actual endpoint reachability, path observations and, where available, independently sourced routing evidence. **Control:** unrelated domain and authorized service in the same observation window. **Limit:** DNS SERVFAIL alone is not evidence of BGP withdrawal, and a trace cannot establish administrative responsibility.
10. **Retransmission versus capture artifact.** Wireshark documents [TCP analysis](https://www.wireshark.org/docs/wsug_html_chunked/ChAdvTCPAnalysis.html) and [TCP reassembly limitations](https://www.wireshark.org/docs/wsug_html_chunked/ChAdvReassemblySection.html): missing captured segments prevent complete reconstruction. For duplicate ACKs or suspected retransmissions, retain frame references and coverage; compare both endpoints or collector drop information when available. **Control:** an independent capture with known coverage in the same window. **Limit:** one partial capture cannot establish packet loss location, loss rate, or responsibility, and missing packets may be capture artifacts.

## Evidence requirements before any implementation

Keep original values and units, version, exact target and address, protocol/family, sample denominator, monotonic window, process status, bounded raw artifact and hash, parser identity, missing reasons, and relevant privacy scope. A normal/pinned comparison must state which variables were held fixed and which were not; report an ineligible comparison rather than calculating misleading phase differences. For any path or remote-vantage adapter, test real versioned output, timeout, permission denial, unsupported options, empty/truncated records, numeric-only output and protocol differences. Do not classify a tool failure as a business failure. Retain the existing four scoped diagnosis states and explicit counterevidence from the [delivery plan](../delivery-plan.md).
