# Closed-loop practices and candidate tools

**Research checked:** 2026-11-12. This is a proposal, not implemented capability, a standards conformance claim, or an executed incident. No upstream code was installed or run, no target was probed, and no device, service, or ticket was changed. The existing [16 designed cases](deep-triage-cases.md) remain unchanged. This note selects sources for gaps in the proposed [workflow](closed-loop-workflow-proposal.md); the [journeys](closed-loop-scenarios.json) are designs. Documentation at `latest`, `stable`, and default branches can change: verify exact installed releases, licenses, supported platforms, permissions, sample output, and failure behavior before adoption. The numbered source IDs below are also used in the journey catalog.

| ID | Primary source and finding | Application and boundary |
| --- | --- | --- |
| ZSM | [ETSI GS ZSM 009-1 V1.1.1, June 2021](https://www.etsi.org/deliver/etsi_gs/ZSM/001_099/00901/01.01.01_60/gs_ZSM00901v010101p.pdf) describes closed-loop governance, coordination across management domains, escalation, and action logging. | Borrow the lifecycle, coordination and audit questions. This proposal does not implement or claim ZSM conformance; an operator-mediated incident path is not ZSM's automated architecture. |
| INTENT | [RFC 9315](https://www.rfc-editor.org/rfc/rfc9315.html) defines intent as declarative operational goals and outcomes and discusses feedback and reconciliation. It is informational. | Express recovery as an affected-service outcome, distinct from commands or device settings. This alone does not establish an intent-based system. |
| SRE | Google's [incident guide](https://sre.google/resources/practices-and-processes/incident-management-guide/) and [postmortem chapter](https://sre.google/sre-book/postmortem-culture/) describe incident roles, follow-up and blameless learning. | Preserve ownership, handoff, timeline and learning after restoration. A postmortem can remain pending without pretending recurrence prevention is complete. |
| NETBOX | [NetBox planning](https://netboxlabs.com/docs/netbox/getting-started/planning/) distinguishes agreed authoritative data and notes that a cable connection validation cannot establish that the cable should be there. | Optional inventory can map service, endpoint, interfaces and ownership. Capture source, as-of time, confidence and mismatch; intended topology is not proof of current forwarding or physical state. |
| PROM | [Prometheus multi-target exporters](https://github.com/prometheus/docs/blob/main/docs/guides/multi-target-exporter.md) describe network collection via a separate exporter; [snmp_exporter](https://github.com/prometheus/snmp_exporter/blob/main/README.md) maps SNMP indices and labels to metrics. | Query existing permitted series first. Interface identity, counter resets, polling interval, missing samples and scrape load matter; an exporter request can itself trigger device traffic. Protect credentials and constrain targets. |
| GNMI | The [OpenConfig gNMI specification](https://github.com/openconfig/reference/blob/master/rpc/gnmi/gnmi-specification.md), version 0.10.0 in the cited document, describes typed paths, timestamps and subscriptions. | A read-only telemetry adapter could map a supported model path to scoped evidence; record target, path, origin, timestamps, subscription gaps and device clock uncertainty. Protocol support and data model coverage vary. |
| SUZIEQ | [SuzieQ](https://suzieq.readthedocs.io/en/latest/) describes agentless collection and normalized network data; its [poller documentation](https://suzieq.readthedocs.io/en/latest/poller/) describes inventory and periodic collection. | An optional read-only consumer can use permitted existing data. Polling adds device, credential and storage costs; stale records, inventory drift, coverage and platform/version support limit conclusions. |
| PYATS | [Cisco pyATS introduction](https://developer.cisco.com/docs/pyats/introduction/) describes pyATS and Genie; Cisco's [pyATS lab guide](https://developer.cisco.com/codeexchange/github/repo/sttrayno/pyATS-Lab-Guide/) demonstrates learning and diffing snapshots. | Snapshot differences can identify a changed state, not automatically explain impact. Match feature, device, collection scope and time; redact configs and check parser coverage. |
| NAPALM | [NAPALM validation](https://napalm.readthedocs.io/en/latest/validate/index.html) compares retrieved live state with expected values; its [configuration tutorial](https://napalm.readthedocs.io/en/stable/tutorials/changing_the_config.html) describes diff and confirmed commit; the [support matrix](https://napalm.readthedocs.io/en/develop/support/) varies by driver. | Getters and validation are candidates for read-only evidence. Configuration diff, rollback and timed confirmation are capability-dependent operator procedures, not assumed atomic, universal or implemented. Never infer business recovery from a compliance report. |
| BATFISH | [Batfish differential reachability](https://github.com/batfish/batfish/blob/master/docs/symbolic_engine/README.md) compares modeled flows between snapshots; [flow dispositions](https://github.com/batfish/batfish/blob/master/docs/flow_dispositions/README.md) notes incomplete snapshots and heuristics. | An optional offline preflight can examine a proposed configuration and affected flows. Record model, snapshot, unsupported features and external boundaries; it cannot establish live physical health, real traffic delivery or an unmodeled network's behavior. |
| ORQUESTA | [Orquesta workflow definition](https://docs.stackstorm.com/orquesta/languages/orquesta.html) specifies failure transitions and bounded retry; [operations](https://docs.stackstorm.com/orquesta/operations.html) explains cancellation and reruns. | Model failed and unknown outcomes explicitly. Cancellation may leave tasks running; rerun is not proof that a remote operation did not happen. Do not add an orchestration service as a prerequisite. |
| JIRA | [Jira Cloud issue transitions](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issues/) are dependent on status and permissions. | A later authorized adapter must discover allowed transitions and reconcile responses; a ticket state is administrative evidence, not proof of technical resolution. No tracker writes are authorized by this research. |
| TMF621 | [TM Forum's Open API directory](https://www.tmforum.org/open-digital-architecture/open-apis) lists TMF621 Trouble Ticket Management; its [conformance report](https://www.tmforum.org/wp-content/uploads/2022/09/AwareX-Final-Report-CEM-Conformance-Certification-Aug-2022-v.1.0.1.pdf) describes a client interface for trouble ticket management among partners. | A possible future handoff interface, subject to version, contract, access and explicit authorization. Listing it does not imply compatibility or certification. |
| CURL | [curl manual](https://curl.se/docs/manpage.html) describes name resolution, connection options and transfer measurements. | Preserve host, SNI, certificate checks, family, proxy, IP and connection semantics when proposing controlled comparisons. |
| ECS | [RFC 7871](https://www.rfc-editor.org/rfc/rfc7871) specifies EDNS Client Subnet and its privacy and caching considerations. | Resolver-dependent answers can reflect steering; different answers do not establish resolver processing delay. |
| HAPPY | [RFC 8305](https://www.rfc-editor.org/rfc/rfc8305) describes dual-stack connection behavior. | Record the actual family and selection; a successful alternative family is scoped mitigation, not proof the original path is repaired. |
| PMTU | [RFC 8201](https://www.rfc-editor.org/rfc/rfc8201) describes IPv6 path MTU discovery and Packet Too Big signaling. | A small successful request does not prove large-flow health; missing feedback or differing path limits conclusions. |
| TCP | [Wireshark TCP analysis](https://www.wireshark.org/docs/wsug_html_chunked/ChAdvTCPAnalysis.html) describes analysis based on captured packets. | Zero-window or retransmission annotations are capture-scoped evidence, not an automatic claim about a remote process or link. |
| FLENT | [Flent test descriptions](https://flent.org/tests.html) document concurrent traffic and latency-under-load tests. | Load testing needs a consenting isolated lab, explicit traffic cap and cleanup; correlation alone is not a production repair justification. |
| BGP | [RFC 7908](https://www.rfc-editor.org/rfc/rfc7908) describes route leaks and their types. | Route evidence can justify an owner handoff; incomplete routing data cannot establish global impact or authorize a policy change. |
| IF | [Linux interface statistics](https://docs.kernel.org/networking/statistics.html) describes interface counters and their semantics. | Counter delta, direction, resets and time matter; errors can support a physical investigation but do not identify a particular optic without additional evidence. |

## Adoption decision

Start with local case records, bounded existing v0.1 observations, manual action records and explicit verification. They need no inventory server or device credentials. Add one read-only data source only after representative sample output, freshness/identity mapping, least privilege, cost, timeouts and absent-data tests exist. Choose the source that answers a recurring case question; a data lake or automation platform is not a prerequisite. Offline modeling and device snapshots are higher-complexity later options. External ticket and execution adapters require a separately approved architecture, authorization, reconciliation, and safeguards; none is delivered here.

First slice exports a draft handoff; ticket closure is not technical resolution. |
| ONAP | [ONAP architecture](https://docs.onap.org/en/paris/ecosystem/architecture/index.html) describes a network automation platform. | Use as a reference for cross-component coordination, not a deployment dependency or proof of capability in this Skill. |
