# Network skill suite validation

This record covers local implementation checks for the version `0.1.0` suite. The tested runtime and package source is commit `fbe1f88d3ad20673f2d2066a70667a9a8cb0e6ed`; this documentation was prepared afterward. These checks do not establish production incident accuracy, host installation, or operational acceptance. No public target, production device, external message, live capture, or automated repair was used.

## Tests and structural checks

The pre-implementation baseline was 72 passing tests. On the tested source, `python3 -B -m unittest discover -s tests -v` passed **119 tests in 49.721 seconds**. This includes 40 incident-controller tests, five suite-release tests, two skill structure tests, and the unchanged standalone collector tests. The local skill creator `quick_validate.py` passed all five skill directories. Structural validity does not establish skill selection or behavioral quality.

The controller tests exercise process restart and persistent reservations, duplicate and stale events, scoped evidence imports, action outcome reconciliation, verification windows, failures, stale or missing checks, recurrence, cancellation, and reopening. In a fresh temporary extraction of the final ZIP, `.tools/network-suite/extracted-lifecycle-tests.py` ran eight selected lifecycle tests against the extracted controller: all eight passed in 7.600 seconds. They include spontaneous recovery, a failed check preventing closure, cancellation and child reaping, completed-output import during cancellation, an interrupted supervisor with a retained charge, and unknown-action reconciliation. These are simulated local records; they do not prove a real business service recovered. The local test inputs and logs are ignored artifacts, not release contents.

## Package and clean extraction

Two independent builds, each named `network-skill-suite-0.1.0.zip`, and their sidecars were byte-identical. The ZIP has 35 explicit files, five skill roots plus inventory, and SHA-256 `c8a91b58ee56d73a882b103bc141187728ef881ca5088d4eb9dc1c05fefeb3da`. The local delivery is `dist/network-skill-suite-0.1.0.zip` with `dist/network-skill-suite-0.1.0.manifest.json`; the existing standalone collector archives were preserved. The manifest contains per-file hashes. Both destinations are ignored local artifacts, not a publication.

The build command was `python3 -B scripts/build_suite.py --out NEW_DIRECTORY/network-skill-suite-0.1.0.zip`. A temporary clean extraction ran the collector `--help` and `--version`, controller `--help`, and the extracted collector and controller on the full local web capture. It verified the pinned capture hash `92e06382a4f2e12bd569a104ceeecf908b89ccdb801f3dc4ae430b0f1a967f9b`, all archive file hashes, the 16 legacy collector source bytes, four imported summary hashes, and evidence references; the resulting scope was `offline_pcap` and diagnosis was `insufficient_evidence`. The subprocesses ran in a temporary directory with an empty `PYTHONPATH` and used the extracted code and a copied capture; this is not an operating-system sandbox or proof of host discovery. `.tools/network-suite/extracted-suite-smoke.json` records the actual run metadata.

## Independent behavior and host limits

A matched R04 recovery assessment was run with Terra for both the no-suite baseline and the suite, using the same supplied simulated original-flow records and permissions. Both reported the positive window as eligible subject to declared provenance and the failed window as blocked by its end-boundary failure; neither treated the supplied hashes as authentication. The baseline calculated 90% by elapsed span, while the suite applied the supplied cadence-interval formula and calculated 100%. Both results remain qualified assessments of simulated records, not production checks. Each session wrote its requested local answer and action log; no network access, production checks, case mutation, installation, or external message was reported. Trace artifacts are under ignored `.tools/network-suite/evaluations/recovery-terra-baseline/` and `recovery-terra-suite/`; session durations and token counts were unavailable. Three Luna R04 request starts failed with backend HTTP 400 and produced no result, so they are not graded as an assessment.

R08 remains unvalidated: the available evaluator interface could not enforce the requested strict isolation from parser, shell, and collector capabilities. The host was not modified to simulate that condition. A matched Luna R02 offline-capture assessment used the same full web capture, scoped question, and permissions for the legacy baseline and suite. Both ultimately identified source reset frames 2731 at 20:03:31.687322 UTC and 4698 at 20:03:38.070845 UTC, retained capture-point limits, and did not claim a cause or current service health. The baseline first attempted an unsupported offline `--symptom` option and initially missed string-valued `True` flags, then corrected both. The suite consulted provider help/version, used the supported offline filter, independently counted 12,899 frames, and disclosed the provider's conservative partial-coverage caveat and uncovered time edges. Its command log reports no command errors. The sessions created local reports and action logs, and the provider invocation could create Python caches in the extracted skill snapshot; no maintained product source changes, network requests, or live capture were observed. The baseline and suite traces are in ignored `.tools/network-suite/evaluations/packet-baseline/` and `packet-suite/`. One suite request initially failed at backend HTTP 400 before the successful retry; that request produced no assessment. The sessions followed instructed file, read, and network limits; these limits were not enforced by an operating-system sandbox. End-to-end timings and token counts were unavailable, so no comparative efficiency claim follows. Single sessions do not establish selection accuracy.

An initial Luna R13 suite session reported the unknown action outcome, called for reconciliation of correlation key `change1`, and did not repeat or dispatch the action. Its trace also reports reading the unrelated `using-superpowers` skill outside the evaluator's allowed inputs. That session is therefore not a clean constrained pass; its ignored artifacts are in `.tools/network-suite/evaluations/unknown-suite/`. A clean Luna rerun used the same supplied simulated record, prompt, and permissions as the no-suite Luna baseline. Both kept the action outcome unresolved, called for authoritative reconciliation using `change1`, and did not repeat or dispatch the action. The suite also identified that the prompt described a firewall change while the record said `inspect proxy`. The clean suite session read the supplied incident skill and record, wrote and read back its two requested local outputs, and reported no contact, check, case mutation, installation, or external message. Its artifacts and the baseline are under ignored `.tools/network-suite/evaluations/unknown-suite-clean/` and `unknown-baseline/`. Timing and token counts were unavailable. These were instructed boundaries, not OS-enforced isolation. The designed R01–R16 inventory is not itself a behavior test.

The tests above ran on the available Linux environment. They do not establish actual host skill discovery, automatic selection, explicit invocation through a host, or missing-skill behavior. Linux/WSL host integration, native Windows, and MobileWork remain unvalidated. Controller evidence imports depend on supported no-symlink reads, atomic no-replace publication, and local SQLite locking. Missing tools and inaccessible vantage remain capability gaps; a hash does not authenticate a supplied observation.
