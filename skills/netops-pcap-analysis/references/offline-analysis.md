# Offline capture analysis

Use the host's supported skill or executable discovery to locate a trusted provider; do not assume another skill is installed at a sibling path. Check the provider's `--version` and `--help` before use. `internet-access-triage 0.1.x` supports `python <provider>/scripts/diagnose.py --pcap <existing-file> --out <new-directory>`. Keep the user's question as analysis context: the offline invocation does not take the live-only `--symptom` option. Read the resulting manifest, evidence, diagnosis, report, and relevant local artifacts; report unavailable parsing and validation errors rather than filling gaps with guesses.

When using an installed permitted parser such as TShark directly, consult its help and documented display filters for the question, then inspect the relevant fields and frame numbers. If consuming structured output, normalize the parser's actual boolean forms before interpreting them; output formats can represent a flag as a number or a string. A matching frame shows what was captured at that point. Missing packets, asymmetric paths, truncation, clock differences, encryption, and absent endpoint context may prevent attribution or conclusions about the wider flow. Do not treat a parser's transport indicator alone as proof of end-to-end loss or device fault.

For multiple captures, keep each vantage, capture time, and evidence identity separate. Compare only the matching flow and interval when the evidence supports it; name missing intervals and alternative explanations. Do not claim automated multi-vantage correlation or ground truth from filenames.
